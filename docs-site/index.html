A small language with serious boundaries

Make systems
say what they mean.

Vāk is an experimental, statically and strongly typed systems language. It is being built in Rust, lowered through LLVM, and documented as carefully as it is implemented.

MANIFESTO / 01

Correctness before cleverness.

Vāk does not attempt to win by accumulating syntax. Its design authority is the language specification, followed by tests, followed by the compiler implementation. Each milestone must be small enough to understand, test, and explain.

01

Explicit semantics

No implicit nulls. No silent numeric conversions. No pretending an unfinished memory model is safe.

02

Native by design

LLVM handles code generation. Vāk owns the source model, diagnostics, semantic checks, and ABI decisions.

03

Scope is a feature

Modules, generics, concurrency, and FFI wait until the foundations can support them honestly.

LANGUAGE / 03

A compact surface.
Room to grow.

The current language is intentionally small. These examples describe what the compiler supports today—not an aspirational feature list.

Abindings

Immutable unless stated

let answer = 42;
let mut total: I32 = 0;
total = total + answer;

Bindings can be inferred locally or annotated explicitly. Assignment to an immutable binding is a diagnostic.

Bcontrol flow

Braces make structure visible

for item in 0..3 {
  if item == 2 {
    continue;
  }
}

Ranges are ascending and half-open. 0..3 visits 0, 1, and 2.

Cdata

Values with known shape

struct Sample {
  timestamp_ns: U64,
  channel: U32,
  value: F64
}

Fixed arrays and simple structs are supported. Rich aggregate ownership remains future work.

Ddiagnostics

Errors are part of the product

error: type mismatch
  --> main.vak:12:17
   = expected I32
   = found String

Malformed source should produce a located, actionable error—not an ordinary compiler crash.

BOUNDARIES / 05

Honest about safety.

The current memory model is value semantics with compiler-managed local storage. It is a foundation, not a claim of complete memory safety.

✓ implemented now

  • Definite-initialization checks
  • Immutable / mutable assignment checks
  • Conditional initialization joins
  • I32 literal range validation
  • Fixed-array runtime bounds traps
  • Move-only String checks in semantic analysis

× explicitly deferred

  • Complete ownership and borrowing
  • References in LLVM lowering
  • Pointer and unsafe semantics
  • Heap allocation and destruction
  • Integer overflow policy
  • Path-sensitive lifetime analysis
“If a safety guarantee cannot be enforced by the v0.1 compiler, state that explicitly rather than pretending it is memory-safe.”— language engineering brief

NEXT / 07

The next serious boundary.

Do not jump to modules, generics, or a package manager yet. The project materials identify a clear order of operations.

01

Reference-aware LLVM lowering

Represent addresses, pass references through signatures and calls, load through &T, store through &mut T, and define a prohibition or safe rule for returned references.

status detail ↗
02

Full borrow regions and lifetimes

Define lexical regions, expiration, escape checks, field/element borrows, nested borrows, conditional joins, loop behavior, and source-precise conflict diagnostics.

03

Ownership-aware intermediate representation

Introduce an IR only when it has a demonstrated purpose: StorageLive, Move, Copy, BorrowShared, BorrowMut, Drop.

04

Aggregate ownership, destruction, runtime

Only after the above: field-level moves, deterministic drop order, heap rules, cleanup on exits, and a real runtime library.

Do not do next: speculative generics, arbitrary C++ parsing, a custom backend, fake standard-library APIs, or a partial Rust-like ownership hybrid.
